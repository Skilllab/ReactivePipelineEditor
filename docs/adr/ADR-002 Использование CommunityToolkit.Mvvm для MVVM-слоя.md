# ADR 002 — Выбор CommunityToolkit.Mvvm для реализации MVVM

Дата: 2026-09-13 
Статус: принято

#Контекст
- Проект `ReactivePipelineEditor` нацеливается на .NET 10 и использует MVVM-подход в UI-слое.
- Требуется уменьшить шаблонный код (boilerplate) во ViewModel, обеспечить хорошую производительность и простоту тестирования.
- Рассматривается библиотека для поддержки типичных MVVM-паттернов: уведомления об изменениях, команды, внедрение зависимостей, и т.п.

#Решение
- Использовать `CommunityToolkit.Mvvm` (Microsoft.Toolkit.Mvvm, сейчас Community Toolkit MVVM) как основную библиотеку MVVM.

#Аргументы в пользу
- Минимальный overhead: легкая библиотека с малым количеством зависимостей и минимальными аллокациями.
- Source generators: генерируют код компилятором, что уменьшает шаблонный код и ошибки ручной реализации.
- Совместимость: поддержка современных .NET (включая .NET 10) и распространенных UI-стеков.
- Производительность: меньше runtime-аллокаций в сравнении с классическими рефлексивными подходами.
- Поддержка и лицензия: активный проект под лицензией MIT, хорошая документация.
- Удобство тестирования: ViewModel остаются POCO-подобными и легко мокируются/тестируются.

#Альтернативы и причины отказа
- Prism: мощный, но тяжелый и избыточный для текущих задач.
- ReactiveUI: сильная реактивная модель, добавляет Reactive технологии в проект; избыточно если не нужен полный reactive-стек.
- MVVM Light и другие устаревшие проекты: ограниченная поддержка и устаревание.
- Самописный MVVM: полная гибкость, но большой объем шаблонного кода и риск ошибок.

#Недостатки и риски
- Зависимость от внешней библиотеки (версионирование, обновления). Необходимо зафиксированием версии.
- Возможные несовместимости при интеграции с очень специфичными фреймворками UI — тестировать интеграцию.

#План миграции (рекомендовано)
1. Добавить пакет: `CommunityToolkit.Mvvm` в соответствующие проекты UI/ViewModel.
2. Выбрать небольшую ViewModel для пилота: заменить ручной `INotifyPropertyChanged` на `ObservableObject` или `partial class` + `[ObservableProperty]`.
3. Заменить реализации команд на `RelayCommand`/`AsyncRelayCommand`.
4. Покрыть измененные ViewModel юнит-тестами.
5. Постепенно перенести остальные ViewModel, документировать шаблоны использования.
6. Зафиксировать версию пакета в `Directory.Packages.props` или `nuget.config`.

#Примеры (минимум кода)

```
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

public partial class SampleViewModel : ObservableObject
{
	[ObservableProperty] private string name;
	public IRelayCommand SaveCommand { get; }
	
	public SampleViewModel()
	{
		SaveCommand = new RelayCommand(OnSave, CanSave);
	}

	private void OnSave() { /* ... */ }
	private bool CanSave() => !string.IsNullOrEmpty(name);
}
```

#Вывод
- `CommunityToolkit.Mvvm` обеспечивает наилучший компромисс: минимальный шаблонный код, хорошая производительность, и простота поддержки. Рекомендуется принять и постепенно внедрять в UI/VM-слой.
